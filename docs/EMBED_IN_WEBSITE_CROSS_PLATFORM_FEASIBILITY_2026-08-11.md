# Cross-Platform Embed Feasibility Check — Joomla, Webflow, Squarespace

Analysis only. No files changed. Findings are based on each platform's current official documentation (cited per claim below).

## Hard constraints that affect the shared architecture

1. **No platform forces an isolated container.** Joomla, Webflow and Squarespace all inject custom code directly into the page DOM by default; none wraps SameView content in an iframe. This *confirms* — rather than changes — the direction already set in the previous analysis: the shared runtime's multi-instance DOM-ID collision (fixed literal `id="sameview-*"`, single `initComparisonPresentation()` call per document) is a SameView-side defect to fix, not something a platform's isolation model would paper over or force a different design for.
2. **CSS host-isolation must be self-defended everywhere**, since no platform offers cascade isolation by default. The shared Presentation CSS needs to remain (or become more) defensively scoped — this applies identically across all three researched platforms and to WordPress/Joomla; it is a shared-foundation requirement, not a platform-specific one.
3. **No generic static-file hosting on Webflow or Squarespace.** Both require the runtime/CSS to be deliverable as inline text within a size-bounded custom-code field, not only as linked files the way a self-hosted CMS plugin ships them. If the shared output-generation code path is designed only around "produces separate files," it will need an inline-text delivery mode later. This doesn't need to be built now, but it should not be foreclosed while designing WordPress's (file-based) packaging.
4. **"Load the runtime once per page, only on pages with a placement" is achievable on all three, but through different mechanisms** — Joomla via its module/plugin system, Webflow and Squarespace via their own *page-level* (not global) custom-code fields. The shared design should treat "conditional per-page loading" as a per-platform responsibility with a common contract, not assume a WordPress-style enqueue API generalizes directly.

## Constraints that are platform-local only

- **Webflow:** paid-plan/workspace gating for Code Embed; \~50,000-character per-field ceiling (size of the shared runtime against this limit is unverified and should be checked); no default CSP on standard hosting (only relevant on Enterprise Custom Hosting).
- **Squarespace:** JavaScript/iframe support excluded on the lowest plan tier; \~300,000-character per-block ceiling (comfortable headroom); default CSP behavior is undocumented/unresolved and should be verified against a live site rather than assumed.
- **Joomla:** risk is entirely avoidable by packaging SameView as a real module/plugin extension (bypassing the filtered Custom HTML text field and its WYSIWYG reformatting risk) — a packaging choice, not a platform ceiling.

## Can WordPress architecture now be designed safely?

Yes, with one discipline carried forward rather than a blocker resolved: **design WordPress's asset delivery as file-based (its natural fit, via the enqueue system) without hard-coding an assumption into the** ***shared*** **`sameview-web`** **generation code that output assets are always separate files.** Nothing found on Joomla, Webflow or Squarespace forces a different interaction model, a different isolation strategy, or blocks runtime language detection — so none of them creates a cross-platform dead end for a WordPress-first design. The only thing that *would* create a later dead end is if WordPress-specific work bakes a files-only packaging assumption into the shared foundation itself; keeping that boundary flexible is enough to proceed on WordPress now without foreclosing Webflow/Squarespace later.
